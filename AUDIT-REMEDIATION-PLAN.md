# План исправления слабостей системы заказов

Дата: 18 октября 2026 г.

## Статус работ

Исправления внесены в локальную ветку `security/remediation-oct18` на основе текущего GitHub `main`. Production-сборка проходит с включёнными проверками ESLint и TypeScript; `npx tsc --noEmit` также проходит. Изменения не отправлялись в GitHub и не проверялись в staging.

До production остаются: миграция старых CBC-резервных копий (новый код принимает только AES-256-GCM v2); проверка восстановления новой копии; проверка переменных Vercel и Google Drive в целевом деплое; регрессионные проверки между компаниями и нагрузочные проверки в staging. Next.js обновлён до поддерживаемой ветки 15.5.28, production `npm audit --omit=dev` сообщает 0 уязвимостей. Полный `npm audit` всё ещё отмечает уязвимости в dev-зависимостях Tailwind/PostCSS; исправление доступно через major-обновление Tailwind 4 и требует отдельной миграции CSS-конфигурации. Ветка не публиковалась и не проверялась в staging; до этих проверок её нельзя считать готовым production-релизом.

## Назначение и границы

План подготовлен по результатам статического аудита исходного кода. Он охватывает выявленные риски конфиденциальности, авторизации, управления секретами, загрузки файлов, контроля качества релиза и производительности. Фактическая конфигурация production, облачных аккаунтов и базы данных в аудит не входила; соответствующие проверки включены отдельным этапом.

**Рекомендация по запуску:** не выдавать широкому кругу пользователей рабочие аккаунты до закрытия критических пунктов Этапа 0 и проверки их критериев приёмки.

## Приоритеты

- **P0 — блокирует запуск:** утечка данных между компаниями, раскрытие ключа резервных копий, небезопасное создание первого администратора, пробелы в актуальности сессий/прав.
- **P1 — высокий:** утечка хеша пароля в ответе API, слабая защита входа и паролей, доверие к параметрам клиента, недостаточное ограничение загрузок, выключенные проверки сборки.
- **P2 — надёжность и эксплуатация:** проверка резервных копий, контроль нагрузки, аудит журналирования и процедуры реагирования.

## Этап 0. Закрыть блокирующие риски до начала работы пользователей

### 0.1. Устранить раскрытие данных продаж в клиентской аналитике

**Область:** `src/lib/analytics/index.ts`, `src/lib/analytics/customer.ts`, `src/app/api/analytics/route.ts`.

1. В ветке клиентской аналитики удалить загрузку заказов всей системы для построения клиентского ответа.
2. Вычислять любые «системные» агрегаты только на сервере для ролей с отдельным разрешением; клиентам возвращать метрики лишь по собственной компании либо собственному аккаунту.
3. Запретить клиенту передавать произвольный `companyIds` для выбора области данных. Для сотрудника проверять соответствующее разрешение и допустимый набор компаний; для клиента всегда принудительно использовать `session.companyId`.
4. Проверить все поля ответа клиентской аналитики: названия товаров, рост, суммы, количества, даты и агрегаты не должны выводить информацию из заказов другой компании.
5. Проверить ответы с пустым, отсутствующим, неверным и чужим `companyId`.

**Критерии приёмки:** тестовый пользователь компании A не получает никаких данных/агрегатов, вычисленных из заказов компании B; подмена `companyIds` не меняет область доступа; сотрудник получает только тот объём данных, который разрешает его роль.

### 0.2. Скрыть ключ шифрования и закрыть доступ к настройкам Google Drive

**Область:** `src/app/api/admin/gdrive/route.ts`, `src/lib/security.ts`, хранилище секретов и интерфейс настроек.

1. Удалить `encryptionKey` из JSON-ответа `GET /api/admin/gdrive`; не возвращать его и в интерфейсе после сохранения. Для подтверждения настройки показывать только факт наличия ключа/время последней ротации.
2. Заменить проверку доступа через список альтернативных разрешений на одно специально предназначенное административное разрешение с минимальным числом пользователей. Перепроверить аналогичные GET-операции с конфиденциальной конфигурацией.
3. Запретить общий ключ `B2BSecureSystemPassphrase2026` и любые автоматические значения по умолчанию. Секрет должен быть случайным, с достаточной энтропией, заданным через менеджер секретов окружения; приложение должно отказывать в операции резервирования/восстановления, если ключ не настроен.
4. Перенести ключ из `SystemSetting` в защищённое хранилище секретов, если это поддерживает окружение. Если временно ключ остаётся в БД, ограничить его чтение и никогда не возвращать через API.
5. Перейти с AES-CBC без проверки подлинности на формат с аутентифицированным шифрованием (например, AES-256-GCM): уникальный nonce, authentication tag, версия формата; предусмотреть миграцию/повторное создание старых резервных копий.
6. Ротировать все ранее использовавшиеся ключи и считать копии, зашифрованные общим ключом, потенциально доступными постороннему.
7. Исключить передачу refresh token Google Drive и других секретов в клиентские ответы и обычные журналы.

**Критерии приёмки:** ни одна роль без целевого административного права не читает/меняет настройки; ответы API, журналы и браузерная сеть не содержат ключей; резервная копия не расшифровывается при неверном ключе или изменённом ciphertext.

### 0.3. Сделать первичную настройку одноразовой и атомарной

**Область:** `src/app/api/auth/setup/route.ts`, схема БД и миграция.

1. Перестать использовать проверку количества пользователей как единственную защиту от повторной настройки.
2. Ввести атомарный признак завершения установки (например, системную запись с уникальным ключом или отдельную таблицу/ограничение). Блокировать его транзакционно до создания первого администратора и шаблонов ролей.
3. Обеспечить, чтобы два параллельных запроса не могли создать двух первоначальных супер-администраторов. Повторный POST после завершения установки должен всегда отказывать без побочных эффектов.
4. Не выполнять внешние операции (Google Drive, файловая система) внутри длинной транзакции. После успешного commit выполнять их как повторяемые фоновые задачи; их сбой не должен откатывать или раскрывать учётную запись.
5. Валидировать имя, email и пароль по тем же правилам, что и при создании пользователей; нормализовать email и ограничить размер входного JSON.
6. В production отключить мастер настройки после однократного завершения; добавить процедуру безопасного восстановления через администрирование, а не повторный открытый setup endpoint.

**Критерии приёмки:** серия одновременных запросов с пустой БД создаёт ровно одного первоначального администратора; последующие запросы не создают пользователей/роли и возвращают контролируемый отказ.

### 0.4. Унифицировать проверку сессии и актуальных разрешений

**Область:** `src/lib/auth.ts` и все API-маршруты, использующие `getSession`, `requireAuth` или `requirePermission`.

1. Провести инвентаризацию всех методов API и назначить каждому минимально необходимое разрешение.
2. Для защищённых операций использовать единый async-механизм, который проверяет подпись/срок JWT, существование аккаунта, `isActive`, актуальную `sessionVersion` и живые разрешения из БД.
3. Не доверять длительно разрешениям и роли из JWT после изменения назначения роли или компании. При изменении роли, компании, активности или пароля увеличивать `sessionVersion`; обеспечить немедленное или документированно ограниченное по времени прекращение сессии на всех экземплярах приложения.
4. Пересмотреть синхронные helper-функции и исключить их использование в маршрутах с данными/изменениями. Для отказа БД при проверке прав использовать fail-closed поведение.
5. Перепроверить логику супер-администратора: обход прав должен определяться устойчивым идентификатором системной роли, а не только изменяемым отображаемым именем или устаревшим legacy-полем.
6. Возвращать корректные коды 401/403, не превращая внутренние ошибки авторизации в 500 и не раскрывая детали токена.
7. Проверить атрибуты cookie в целевом production: `HttpOnly`, `Secure`, `SameSite`, срок действия и согласованность срока cookie с JWT.

**Критерии приёмки:** деактивация пользователя, смена пароля или роли прекращает доступ к защищённым API; старый JWT не сохраняет прежние права; отказ хранилища прав не открывает доступ.

## Этап 1. Устранить высокие риски управления аккаунтами и запросами

### 1.1. Исключить возврат passwordHash из API управления пользователями

**Область:** `src/app/api/admin/users/route.ts`.

1. Во всех ответах POST/PUT/GET формировать явный безопасный DTO с разрешёнными полями (`id`, `email`, `name`, роль, компания, статус и даты).
2. Для обновления использовать `select` Prisma с белым списком полей или отдельную функцию сериализации. Не возвращать необработанную запись модели.
3. Проверить сериализацию ошибок и аудит-логов: пароль и хеш не должны попадать туда даже при исключениях.
4. Инвалидировать сессии обновляемого пользователя при смене пароля/роли/компании/статуса.

**Критерии приёмки:** ни один ответ API управления пользователями не содержит `passwordHash`, пароль или секретные поля.

### 1.2. Усилить защиту входа и политики паролей

**Область:** `src/app/api/auth/login/route.ts`, `src/app/api/auth/change-password/route.ts`, API создания/сброса пользователя, схема и middleware/хранилище rate limit.

1. Внедрить ограничение попыток входа с учётом IP и нормализованного аккаунта. Использовать общее хранилище, работающее между serverless-инстансами, с экспоненциальной задержкой/временной блокировкой и защитой от чрезмерной блокировки чужой учётной записи.
2. Вести безопасный журнал неудачных входов без пароля, токена и чрезмерных персональных данных; ограничить срок хранения и доступ.
3. Повысить минимум пароля (например, не менее 12 символов для пользовательского пароля; отдельно согласовать корпоративную политику), проверять максимальную длину и не обрезать пароль молча.
4. Для первоначально выданных паролей использовать одноразовую ссылку/код установки пароля с коротким сроком действия, а не общий пароль для группы пользователей.
5. При сбросе/смене пароля увеличить версию сессии и завершить остальные сессии. Рассмотреть подтверждение через текущий пароль и дополнительную проверку для привилегированных аккаунтов.
6. Сохранять bcrypt с обоснованной стоимостью либо планировать современную password-hashing схему; любые изменения сопровождать проверкой производительности и безопасной миграцией.
7. Возвращать одинаковое сообщение для отсутствующего пользователя и неверного пароля, не раскрывая существование аккаунта.

**Критерии приёмки:** лимит действует на всех экземплярах; пароль слабее политики не принимается ни через UI, ни через прямой API; после смены пароля старые сессии отклоняются.

### 1.3. Защитить API расчёта заказа и уточнить права аналитики

**Область:** `src/app/api/orders/calculate/route.ts`, `src/app/api/analytics/route.ts`, сервисы аналитики и расчёта.

1. Для расчёта требовать авторизацию и разрешение на создание/расчёт заказа. Если endpoint намеренно публичный, ограничить его нагрузку и выдаваемую информацию, а также явно обосновать этот режим.
2. Клиентский `companyId` игнорировать. Для обычного пользователя брать компанию из текущей записи пользователя/проверенной сессии; для сотрудника проверять право действовать от имени выбранной компании.
3. Проверять доступность каждого `productId`/`groupId`, допустимые количества и цену на стороне сервера. Клиентская цена не должна считаться источником истины.
4. Проверить, что расчёт не раскрывает непубличные промо-правила, остатки склада или данные других компаний.
5. На аналитике требовать отдельное `analytics:view`; отдельно проверять доступ к аналитике своей компании и общей аналитике.
6. Ограничить временной диапазон, число идентификаторов компаний и размер ответа, чтобы запросы с огромным периодом не создавали нагрузку на БД.

**Критерии приёмки:** прямой запрос без нужного права отклоняется; изменение тела запроса или query-параметров не позволяет выйти за область пользователя; серверная цена и права на товары подтверждены.

### 1.4. Ввести безопасные ограничения загрузки файлов

**Область:** `src/app/api/orders/[id]/documents/route.ts`, `src/lib/orders/order-document.service.ts`, инфраструктурные лимиты.

1. Ограничить максимальный размер запроса на уровне ingress/platform до разбора multipart; обработчик должен проверить размер до преобразования всего файла в буфер, насколько позволяет runtime.
2. Установить лимиты на файл, суммарный multipart-запрос и частоту загрузок на пользователя/заказ.
3. Проверить сигнатуру фактического содержимого для всех типов. Для изображений при возможности декодировать и пересохранить безопасно; для Office-документов защититься от ZIP-бомб и избыточного размера распаковки.
4. Сверять расширение, сигнатуру и разрешённый MIME; недоверенный `file.type` использовать только как подсказку.
5. Очищать имя файла, использовать случайное имя хранения, не допускать путь/URL от клиента к файловой системе, ограничить типы документов и их доступ по роли/заказу.
6. Проверить, что хранилище документов закрытое, а скачивание всегда проходит серверную авторизацию и проверку принадлежности компании. Публичный bucket допустим только для неперсональных изображений каталога.
7. Определить срок хранения водительских удостоверений и документов на транспорт, доступ к ним, аудит скачиваний и порядок удаления.

**Критерии приёмки:** превышение лимита отклоняется до значительного потребления памяти; несоответствие сигнатуры расширению блокируется; чужой пользователь не может загрузить/скачать документ через подмену ID.

### 1.5. Включить проверки качества в production-сборке

4. Защитить production deploy правилом: выпуск разрешён только при успешном CI и проверенной миграции БД.

**Критерии приёмки:** намеренная ошибка TypeScript и lint приводит к провалу сборки/CI; корректная ветка проходит весь обязательный pipeline.

## Этап 2. Эксплуатационная надёжность, резервирование и контроль доступа

### 2.1. Проверить backup/restore и жизненный цикл секретов

1. Составить перечень данных, входящих в каждую резервную копию; хранить только необходимые поля и не включать секреты без необходимости.
2. Установить отдельные права и аудит для запуска backup/restore. Восстановление должно требовать повторного подтверждения привилегированного администратора и проверки целостности/версии формата.
3. Перейти от локального mock-хранилища Google Drive к явному production fail-closed режиму: если облако не настроено, сообщать об ошибке, а не незаметно писать рабочие файлы в локальную файловую систему.
4. Проверить, что резервные копии приватны, доступны только сервисному аккаунту и ограниченной группе администраторов, имеют версионирование и политику хранения.
5. Регулярно выполнять тестовое восстановление в изолированную среду. Проверять, что восстановление не перезаписывает действующих пользователей и не возвращает старые права/сессии без контроля.
6. Документировать ротацию ключей и аварийное восстановление при их утрате.

**Критерии приёмки:** успешное восстановление проверено на копии в тестовой среде; ошибочный ключ/повреждённый файл отклоняется; production не сохраняет документы в локальный mock.

### 2.2. Подтвердить разделение доступа во всех сущностях

Провести матрицу ролей и проверить на прямых API-запросах:

- чтение, создание, изменение и удаление заказов;
- смена статуса и принятие заказа;
- экспорт Excel и просмотр документов;
- комментарии и история действий;
- компании, пользователи, товары, цены и складские остатки;
- аналитика и доступ к периодам/фильтрам;
- шаблоны, акции, импорт, журналы, Google Drive и настройки.

Для каждого запроса проверить: владелец внутри своей компании, другой пользователь той же компании, пользователь чужой компании, менеджер с ограниченной ролью, логистика, бухгалтерия, администратор, деактивированный пользователь и неавторизованный клиент.

**Критерии приёмки:** проверка проводится на уровне каждого API/service, а не только в интерфейсе; чужой идентификатор в URL/body не расширяет права; записи/объекты другого tenant не возвращаются даже частично.

### 2.3. Подтвердить производительность и отказоустойчивость заказов

1. Пересмотреть вывод документа `PERFORMANCE-CAPACITY-ANALYSIS.md` на актуальных коде, конфигурации и production-профиле; документ мог быть подготовлен для другой версии.
2. Зафиксировать ожидаемые пиковые параллельные оформления, объёмы заказов и размеры каталога.
3. Провести безопасное нагрузочное тестирование только в staging с копией/синтетическими данными и подтверждённым запретом на production target.
4. Измерить задержки и ошибки создания заказа, очередь соединений Prisma/PgBouncer, блокировки транзакций, размер serverless-функций, память и время генерации документов.
5. Настроить лимиты соединений и таймауты с учётом числа инстансов serverless; контролировать медленные запросы, рост очереди и ошибки транзакций.
6. Проверить идемпотентность повторной отправки заказа при сетевом таймауте, чтобы повторы не создавали дубликаты и не списывали товар/бюджеты акции повторно.

**Критерии приёмки:** согласованный целевой уровень параллельной нагрузки достигается без потери/дублирования заказов и неприемлемой доли ошибок; есть метрики и пороги оповещения.

### 2.4. Усилить аудит и наблюдаемость

1. Зафиксировать события входа (успех/ошибка), изменения роли и компании, смены пароля, создания/блокировки аккаунта, экспорта, доступа к документам, операций с backup/restore и критических изменений заказов.
2. Не записывать пароли, JWT, refresh token, ключи шифрования и содержимое документов; ограничить и нормализовать IP/UA согласно внутренним правилам обработки данных.
3. Ограничить доступ к журналам, защитить от изменения/удаления обычными администраторами и определить срок хранения.
4. Добавить мониторинг ошибок API, отказов входа, аномального скачивания/экспорта, исчерпания пула БД, неуспешных backup и всплеска загрузок.
5. Подготовить процедуру блокировки аккаунта, отзыва сессий, ротации секретов и уведомления ответственных при инциденте.

## Этап 3. Проверки перед открытием аккаунтов

1. Развернуть исправленную версию в staging с production-похожими настройками, но тестовыми данными и секретами.
2. Создать минимум две тестовые компании и аккаунты для каждой роли; заполнить заказы и документы, которые нельзя пересекать между компаниями.
3. Выполнить регрессионные проверки всех критериев приёмки Этапов 0–2. Проверять API напрямую, минуя frontend.
4. Проверить production переменные и секреты: `JWT_SECRET`, `DATABASE_URL` с правильным режимом пула, ключ резервирования, Google OAuth, URL callback, лимиты хранилища и ограничения запросов. Убедиться, что `JWT_SECRET` уникален и достаточно случаен, а тестовые credentials не используются.
5. Проверить миграции, индексы, восстановление backup, домен/TLS, cookie `Secure`, логи и алерты.
6. Оформить решение о запуске: список закрытых P0/P1, остаточные риски, ответственные и проверенная дата backup/restore.
7. Запускать пользователей волнами: внутренняя команда → ограниченная группа клиентов → остальные. После каждой волны отслеживать ошибки доступа, заказы, загрузки и нагрузку.
